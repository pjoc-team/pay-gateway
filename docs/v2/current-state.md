# v2 设计输入：现状与差距

审阅基线：`pay-gateway@f6258c0`；历史文档版本见 [来源清单](../pay/SOURCE.json)。这是静态阅读结论，未运行旧系统，也未确认生产使用情况。

## 文档与代码的对应

| 领域 | 文档意图 | 仓库证据与重构含义 |
| --- | --- | --- |
| 交易入口 | 验签、下单、渠道路由 | `pkg/gateway/service.go` 的 `Pay` 已编排此流程；直接依赖外部 protobuf 与服务发现 |

## 重构必须解决的问题

1. `SavePayOrderOk`、`SavePayNotifyOk` 虽创建 `tx`，后续写操作使用 `s` 而非 `tx`；新设计要求同一事务句柄完成相关写入，并用回滚测试验证。
2. 支付成功与通知任务分开保存，存在进程在两者之间退出的窗口；用同事务 outbox 消除本地双写窗口。
3. 请求到达渠道后超时，不能只映射成普通系统失败；需持久化支付尝试并查单恢复，避免重复扣款。
4. 回调、主动查单和对账会并发更新同一笔订单；需要版本检查、事件去重与统一状态转换入口。
5. 成功记录和通知记录分散，增加了检索与一致性成本；v2 以单一交易主记录为事实源，通知、退款、账务独立建模。
6. 原架构的 Mycat／MGR／Otter 双向同步为历史方案；首期采用单写权威库，跨地域写入设计需另立专题验证。

## 保留的原则

渠道适配器不修改订单；对外协议统一；回调按渠道格式应答；异步通知可重试；后督与对账互补；交易与商品、营销、发货解耦。
